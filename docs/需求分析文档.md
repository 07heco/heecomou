## 1. 产品概述

### 1.1 产品定义

**HeecoMou** 是一款面向全平台（手机端 + 电脑端）的智能语音输入法产品，核心采用 **"端云混合 ASR 引擎 + 跨端上下文感知 + 智能场景路由"** 架构，帮助用户在任意设备、任意场景下以最高效率完成文本输入。

### 1.2 产品愿景

让语音输入从「可用」进化为「好用且可信赖」—— 用户无需关心网络状况、设备差异、环境噪声，随时随地开口即所得，跨设备无缝衔接。

### 1.3 核心价值主张

| 维度 | 传统语音输入法 | HeecoMou |
|------|---------------|----------|
| 准确度 | 云端依赖，离线不可用 | 端侧 0.6B 模型离线可用 + 云端 1.7B 高精度兜底 |
| 响应速度 | 全云端 500ms~2s | 端侧 < 200ms，流式逐字上屏 |
| 跨设备 | 各端独立，词库不互通 | 用户词库/偏好云端同步，一处学习处处生效 |
| 成本 | 商业 API 按量计费 | 开源模型自主部署，边际成本趋零 |
| 隐私 | 全量音频上传云端 | 离线模式本地处理，「音频不出设备」 |

## 2. 市场现状与竞品痛点分析

基于对 20 款主流语音输入法产品（讯飞、搜狗、百度、微信、抖音、Google、Apple、微软、三星、华为、荣耀、小米、讯飞听见、Wispr、闪电说、Spokenly、豆包、Cursor、GitHub Copilot、系统自带）的深度用户反馈分析，我们提取了以下 **六大核心痛点** 作为本产品的切入点：

### 2.1 痛点一：离线不可用或离线识别质量断崖式下降

- **现象**：大多数商业输入法依赖云端 ASR 引擎，在地铁、电梯、地下室等弱网/无网环境中完全不可用。少数支持离线识别的产品（如讯飞）在离线模式下准确率大幅下降 30%~50%。
- **根因**：端侧模型体积受限（< 200MB），无法承载高精度大模型。
- **HeecoMou 方案**：采用 Qwen3-ASR-0.6B 端侧部署 + 模型量化压缩，在 200MB 体积内实现接近云端 85% 的识别精度，离线可用。

### 2.2 痛点二：跨设备体验割裂

- **现象**：用户在手机上积累的个性化词库（人名、术语、常用短语）无法同步到电脑端；每次切换设备都需要重新「训练」输入法。
- **根因**：各端输入法为独立产品线，缺少统一的用户画像与词库同步机制。
- **HeecoMou 方案**：基于 Java 后端构建统一用户画像云服务，用户词库、纠错历史、偏好设置全端实时同步。

### 2.3 痛点三：嘈杂环境识别率骤降

- **现象**：咖啡馆、地铁、开放办公室等场景下，现有产品的识别准确率从 95% 降至 60%~70%。
- **根因**：前端缺乏自适应降噪，后端模型对带噪音频泛化能力不足。
- **HeecoMou 方案**：Go 网关层集成环境噪声等级检测 + 自适应降噪预处理，Python ASR 服务端部署专为噪声鲁棒优化的 Qwen3-ASR 模型。

### 2.4 痛点四：方言与中英混说支持薄弱

- **现象**：非标准普通话用户（方言使用者、中英夹杂的技术人员）识别体验极差。
- **HeecoMou 方案**：Qwen3-ASR 原生支持 22 种中文方言 + 30 种外语 + 中英混合识别，配合 Java 后端领域词库注入，精准覆盖多语场景。

### 2.5 痛点五：长文本输入上下文丢失

- **现象**：连续口述长文时，后文识别缺乏前文语境约束，导致同音词频繁误判。
- **HeecoMou 方案**：Python NLP 后处理模块引入滑动窗口上下文语义纠错，利用前文 200 字的语义信息修正当前识别结果。

### 2.6 痛点六：成本高企与隐私顾虑

- **现象**：商业 ASR API 按时长计费（讯飞约 ¥3~5/小时），高频用户成本不菲；全量音频上传云端引发隐私焦虑。
- **HeecoMou 方案**：开源模型自主部署，端侧离线模式实现「音频不出设备」，云端仅处理用户主动选择的复杂场景。

### 4.2 功能详细说明

#### F1. 端云混合语音识别引擎

| 子功能 | 描述 | 优先级 |
|--------|------|--------|
| F1.1 端侧离线 ASR | Android/iOS/Desktop 集成 Qwen3-ASR-0.6B，模型量化至 <200MB，支持纯离线推理 | P0 |
| F1.2 云端高精度 ASR | Python 服务部署 Qwen3-ASR-1.7B，GPU 推理，提供 gRPC 流式接口 | P0 |
| F1.3 智能路由决策器 | 根据网络质量（RTT/丢包率）、环境噪声等级、设备电量、用户偏好，自动选择端侧或云端引擎 | P0 |
| F1.4 流式增量识别 | 音频分块（200ms/chunk）实时传输，逐字/逐词上屏，用户感知延迟 < 300ms | P0 |

**智能路由决策逻辑**：

```
IF 无网络连接 → 强制端侧
ELSE IF 环境噪声等级 > 阈值 AND 设备电量 > 20% → 云端高精度
ELSE IF 用户偏好设置 = "隐私优先" → 端侧
ELSE → 云端（默认：准确度优先）
```

#### F2. 自适应音频预处理

| 子功能 | 描述 | 优先级 |
|--------|------|--------|
| F2.1 环境噪声检测 | 实时分析音频信号，输出噪声等级（静音/安静/一般/嘈杂/极噪） | P0 |
| F2.2 自适应降噪 | 基于噪声等级选择降噪策略（轻度 Wiener 滤波/重度 DNN 降噪），Go 网关层处理 | P0 |
| F2.3 智能 VAD | 基于能量+深度学习双阈值 VAD，自适应环境噪声，减少无效音频上传 | P1 |

#### F3. 跨设备上下文同步

| 子功能 | 描述 | 优先级 |
|--------|------|--------|
| F3.1 用户词库同步 | 用户添加的自定义词汇、高频词权重实时同步至所有登录设备 | P0 |
| F3.2 纠错历史共享 | 用户在任一设备上纠正的识别错误，同步至云端并在其他设备生效 | P0 |
| F3.3 偏好漫游 | 语言偏好、方言设置、隐私模式等配置跨端同步 | P1 |
| F3.4 设备管理 | 查看/管理已登录设备，支持远程踢出 | P2 |

#### F4. 智能文本后处理

| 子功能 | 描述 | 优先级 |
|--------|------|--------|
| F4.1 上下文语义纠错 | 利用前文 200 字窗口 + 轻量级语言模型，修正同音词/近音词误判 | P0 |
| F4.2 领域词汇注入 | 根据当前应用场景（代码编辑器/微信/Word 等），自动注入领域热词 | P1 |

## 5. 非功能性需求

### 5.1 性能指标

| 指标 | 端侧模式 | 云端模式 | 备注 |
|------|---------|---------|------|
| 首字上屏延迟 | < 200ms | < 300ms | 从用户停止说话到第一个字出现 |
| 流式逐字延迟 | < 100ms/chunk | < 150ms/chunk | 每 200ms 音频块的识别延迟 |
| 端侧模型体积 | < 200MB（量化后） | N/A | 移动端可接受范围 |
| 内存占用 | < 500MB（推理峰值） | N/A | 移动端 |
| CPU 占用率 | < 30%（持续推理） | N/A | 不影响前台应用 |

### 5.2 准确度指标

| 场景 | 端侧（0.6B） | 云端（1.7B） |
|------|------------|-------------|
| 安静环境普通话 | ≥ 93% CER | ≥ 97% CER |
| 嘈杂环境普通话 | ≥ 80% CER | ≥ 92% CER |
| 中英混说 | ≥ 85% CER | ≥ 93% CER |
| 常见方言 | ≥ 80% CER | ≥ 90% CER |

### 5.3 安全与隐私

- 端侧模式：音频数据**完全不出设备**，本地处理
- 云端模式：音频传输采用 TLS 1.3 加密，服务端处理后**不落盘存储**
- 用户词库数据：AES-256 加密存储，传输加密
- 账号认证：JWT + OAuth 2.0，支持多因素认证
- 符合《个人信息保护法》要求

|------|---------|------|

## 7. 创新点与差异化优势

### 7.1 核心创新：端云混合智能路由 ASR 架构

**创新描述**：区别于传统「纯云端」或「纯端侧」方案，HeecoMou 首创**自适应混合路由**机制 — 客户端实时感知网络质量、环境噪声、设备算力和用户偏好，动态决策使用端侧 0.6B 模型还是云端 1.7B 模型，实现「该快则快、该准则准」的最优体验。

**受益痛点**：痛点一（离线不可用）、痛点三（嘈杂环境）、痛点六（成本与隐私）

### 7.2 核心创新：跨端上下文感知词库

**创新描述**：基于 Java 后端构建的用户画像云，将词汇偏好、纠错历史、场景标签等特征建模为向量，在 ASR 后处理阶段实时注入，使各端输入法「越用越懂你」，且一处学习处处生效。

**受益痛点**：痛点二（跨设备割裂）、痛点四（方言/混说支持）、痛点五（上下文丢失）

### 7.3 核心创新：三栈协同的最优技术分工

**创新描述**：利用 Go 的高并发网络处理能力（音频流网关）、Java 的企业级业务架构能力（用户系统/数据同步）、Python 的 AI 生态优势（ASR 推理/NLP），实现三栈各司其职、优势互补的架构。

**受益痛点**：痛点六（成本），开源技术栈降低第三方依赖成本

### 7.4 差异化对比

| 对比维度 | 讯飞 | 搜狗 | 微信 | **HeecoMou** |

## 8. 附录：三栈协同分工

### 8.1 Go 技术栈职责

- **音频流网关**：WebSocket/gRPC 高并发音频流接入与转发
- **智能路由器**：实时网络探测 + 路由决策引擎
- **音频预处理 Pipeline**：自适应降噪、Smart VAD、音频格式转码
- **负载均衡与服务发现**：ASR 推理节点的健康检查与流量分发

### 8.2 Java（主栈）职责

- **用户中心服务**：注册/登录、OAuth 2.0 认证、JWT Token 管理
- **词库管理服务**：个人词库 CRUD、热词统计、词频权重计算
- **数据同步服务**：跨设备增量同步（基于版本向量），冲突解决
- **个性化引擎**：用户偏好建模、领域分类、词汇推荐
- **REST API 网关**：统一对外 API，限流/鉴权/日志
- **数据库设计**：MySQL（核心业务）+ Redis（缓存/会话/排行榜）

### 8.3 Python 技术栈职责

- **ASR 推理服务**：Qwen3-ASR-1.7B 部署（vLLM/ONNX Runtime），GPU 推理
- **NLP 后处理**：上下文语义纠错、标点补全、中英格式化
- **模型管理**：模型版本管理、热更新、A/B 测试框架
- **噪声鲁棒增强**：基于 DNN 的语音增强预处理
