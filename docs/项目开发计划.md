## 1. 技术选型深度分析

### 1.0 选型总览

```
┌─────────────────────────────────────────────────────────────────┐
│ 技术栈全景                                                       │
```

### 1.1 为什么选择 Go 做音频流网关（而非 Java/Node.js）

| 考量维度 | Go | Java (Netty) | Node.js | 结论 |
|----------|-----|-------------|---------|------|
| 高并发 WebSocket 连接 | goroutine 轻量，百万连接内存 < 2GB | Netty 优秀但 JVM 内存开销大 | 单线程 event loop，CPU 密集场景弱 | **Go 最优** |
| 音频二进制流处理 | `[]byte` 原生高效，零拷贝 | ByteBuf 灵活但有 GC 压力 | Buffer 操作不如 Go 直观 | **Go 最优** |
| 部署体积 | 静态编译 ~15MB | JRE 依赖 200MB+ | node_modules 臃肿 | **Go 最优** |
| 学习/编码成本 | 语法简洁，上手快 | 生态成熟但繁重 | JS 全栈但音频处理库少 | Go 适中 |
| gRPC 生态 | 官方一等支持 | 优秀 | 一般 | 持平 |

**决策**：Go 做网关层的核心原因是「高并发连接 + 低内存开销 + 二进制流处理天然高效」。音频流网关需要同时维护数千个 WebSocket 长连接并实时转发音频分片，Go 的 goroutine-per-connection 模型是最佳匹配。

**参考开源验证**：[XiaoZhi-Go](https://github.com/wwwAngHua/xiaozhi-go) 项目已验证 Go 在语音流网关场景的可行性。

### 1.2 为什么选择 Java + Spring Boot 做主业务栈

| 考量维度 | Java + Spring Boot | Go (全栈) | Python (Django) | 结论 |
|----------|-------------------|-----------|-----------------|------|
| 业务建模能力 | 强类型 + OOP，复杂业务建模天然适合 | 接口/组合模式，大项目维护成本高 | 动态类型，重构风险高 | **Java 最优** |
| 数据库 ORM | MyBatis-Plus / JPA，SQL 控制力强 | GORM 尚可但不够成熟 | Django ORM 强大但绑定框架 | **Java 最优** |
| 安全生态 | Spring Security，OAuth2/RBAC 开箱即用 | 需手动集成 casbin 等 | Django 内置但定制性差 | **Java 最优** |
| 事务管理 | `@Transactional` 声明式，成熟稳定 | 手动管理，容易遗漏 | Django 事务支持好 | **Java 最优** |
| 生态丰富度 | 全球最大后端生态 | 快速增长中 | AI/数据强，传统业务弱 | **Java 最优** |

**决策**：用户系统、词库管理、数据同步这些业务涉及复杂的数据库关系（用户-设备-词库-纠错历史多对多）、事务一致性、权限控制，正是 Spring Boot + MyBatis-Plus 的擅长领域。

**具体选型理由**：
- **Spring Boot 3.2.x**：最新稳定版，原生支持虚拟线程（Project Loom），提升 IO 密集型场景吞吐
- **MyBatis-Plus 3.5.x**：相比 JPA，手写 SQL 更适合词库的复杂检索（模糊匹配、拼音检索、词频排序）
- **Spring Security 6.x + JWT**：无状态认证，适合移动端 + 桌面端多端登录场景
- **Flyway**：数据库版本管理，每张表的变更都有迹可循，PR 评审时清晰可追溯

### 1.3 为什么选择 Python 做 ASR 推理服务（而非 Java/Go）

| 考量维度 | Python | Java (DJL/Deep Java Library) | Go | 结论 |
|----------|--------|------------------------------|-----|------|
| 模型生态 | PyTorch/HuggingFace 原生支持 | 需通过 DJL 桥接，模型兼容性差 | 几乎无直接支持 | **Python 绝对优势** |
| Qwen3-ASR 兼容 | 官方 Python SDK 唯一支持 | 无官方支持 | 无官方支持 | **Python 唯一选择** |
| ONNX Runtime | 一线支持，文档最全 | 二线支持 | 支持较弱 | **Python 最优** |
| NLP 库生态 | jieba/pypinyin/transformers 成熟 | HanLP 可用但库少 | 库极少 | **Python 最优** |
| GPU 推理 | CUDA/PyTorch 原生 | 需额外适配 | 不支持 | **Python 唯一选择** |

**决策**：Qwen3-ASR 模型的官方推理代码、模型权重加载、tokenizer 全部基于 Python/HuggingFace 生态，这是硬性约束。同时，NLP 后处理（jieba 分词、pypinyin 拼音转换、标点模型）几乎被 Python 生态垄断。用 Python 做这层是**唯一合理选择**，不是偏好问题。

**具体选型**：
- **FastAPI**（非 Flask）：原生异步支持，与 ASR 推理的异步 GPU 调用天然匹配
- **ONNX Runtime**（非 PyTorch 直接推理）：模型导出为 ONNX 后推理速度提升 2~3x，且支持 INT8 量化
- **无 GPU 降级策略**：开发机无 GPU 时，使用 ONNX Runtime CPU 推理 + 模型 INT8 量化，虽然慢（约 3~5x 实时）但可验证功能正确性

### 1.4 为什么选择 Kotlin 做客户端（而非 Flutter/React Native）

| 考量维度 | Kotlin (Native Android) | Flutter | React Native | 结论 |
|----------|------------------------|---------|-------------|------|
| IME（输入法）支持 | Android InputMethodService 原生 API | 需 Platform Channel 桥接，IME 场景不成熟 | 同左 | **Kotlin 唯一可行** |
| 麦克风音频采集 | AudioRecord API 直接访问，延迟 < 50ms | 需桥接，延迟不可控 | 需桥接 | **Kotlin 最优** |
| ONNX Runtime 集成 | AAR 原生包，JNI 直接调用 | 需 FFI 绑定 | 需原生模块 | **Kotlin 最优** |
| 桌面端 | Compose Multiplatform 复用 Kotlin 代码 | Flutter Desktop 成熟 | Electron 体积大 | Kotlin 可复用 |
| 开发效率 | 仅 Android + Desktop，无跨平台损耗 | 一套代码多端但 IME 不可行 | 同左 | — |

**决策**：语音输入法的 Android 客户端本质是一个 **IME（InputMethodService）**，这要求直接使用 Android 原生 API。Flutter/React Native 等跨平台框架在 IME 场景下几乎不可用。Kotlin 是唯一合理选择。

**桌面端用 Compose Multiplatform**：因为同样用 Kotlin，可以共享网络层、ASR 客户端、同步管理等 ~60% 的代码。相比另起一个 Electron/C# 项目，维护成本减半。

### 1.5 为什么选择 Qwen3-ASR 而非 Whisper/Vosk

| 对比维度 | Qwen3-ASR (0.6B/1.7B) | OpenAI Whisper (large-v3) | Vosk | 结论 |
|----------|----------------------|---------------------------|------|------|
| 中文识别精度 | 端侧 93%，云端 97% | ~90% | ~85% | **Qwen3 最优** |
| 方言支持 | 22 种中文方言 | 不支持 | 有限 | **Qwen3 唯一** |
| 中英混说 | 原生支持 | 较差 | 不支持 | **Qwen3 最优** |
| 模型体积（量化后） | 0.6B INT8 ≈ 600MB → Q4 ≈ 200MB | large-v3 ≈ 3GB | small ≈ 40MB（精度差） | Whisper 过大 |
| 开源协议 | Apache 2.0（商用免费） | MIT | Apache 2.0 | 均友好 |
| 流式推理 | 支持 chunk 流式 | 不支持（需完整音频） | 支持 | **Qwen3 + Vosk** |

**决策**：Qwen3-ASR 是当前中文语音识别开源领域的最优选择——精度最高、方言支持最广、模型大小适中（0.6B 量化后可端侧部署）、协议友好（Apache 2.0）。Whisper 的中文能力明显弱于 Qwen3，Vosk 精度差距太大。流式推理能力也优于 Whisper（Whisper 需要完整音频才能输出结果，不支持逐 chunk 增量识别）。

**双版本策略**：
- **0.6B（端侧）**：INT8 → ONNX 导出 → Android ONNX Runtime 加载。目标是 < 200MB、< 200ms 首字延迟
- **1.7B（云端）**：GPU 服务器部署，PyTorch 原生推理。目标是 < 300ms 首字延迟、≥ 97% 安静环境准确率

### 1.6 基础设施选型理由

| 技术 | 选型理由 |
|------|---------|
| **MySQL 8.0** | 用户/词库/设备等关系型数据，需要事务、外键、复杂查询（词库拼音检索） |
| **Redis 7.x** | JWT Token 黑名单、词库热数据缓存、设备在线状态、接口限流计数器 |
| **WebSocket（非 HTTP 短连接）** | 音频流是持续的双向数据流，HTTP 短连接开销过大；WebSocket 长连接 + 二进制帧是最优解 |
| **gRPC（Go ↔ Python 内部通信）** | Go 网关到 Python ASR 的音频流转发，gRPC 双向流比 HTTP 更高效，且支持 Protocol Buffer 序列化 |
| **Docker Compose** | 单人开发环境一键启动全部 5 个服务（Go/Java/Python/MySQL/Redis），避免环境配置踩坑 |
| **GitHub Actions CI** | 每次 PR 自动跑 golangci-lint + Checkstyle + ruff + 单元测试，确保主分支始终可运行 |

| P6 | 成本高 / 隐私顾虑 | 商业 API ￥3~5/小时；音频全量上传云端 | 开源模型自部署（0 边际成本）+ 端侧离线模式（音频不出设备）+ 隐私优先路由策略 | Go（路由决策）+ Python（自部署 ASR） |

## 4. 细粒度 PR 开发计划

> **核心原则**：
> 1. 每个 PR 只做**一个小需求**（一个 API 端点 / 一个功能模块 / 一个页面组件）
> 2. 每个 PR 合并前必须完成**前后端联调验证**
> 3. 主分支始终可运行（每个 PR 合并后 `docker-compose up` 即可跑通现有功能）
> 4. 单人开发，顺序推进，每天 2~3 个 PR

#### PR-010：用户注册 API

- **模块**：`[backend]`
- **需求来源**：F6.1（用户注册）
- **技术方案**：
  - `POST /api/v1/auth/register`
  - 请求体 `{ "username": "...", "password": "...", "email": "..." }`
  - 密码使用 **BCrypt**（`spring-security-crypto`）加密存储——盐值自动生成并嵌入哈希，无需单独存盐
  - 校验：用户名长度 3~20、密码长度 6~30、邮箱格式、用户名/邮箱唯一性

- **关键决策**：BCrypt 而非 SHA-256——BCrypt 自带盐值 + 可调节计算强度（cost factor），是目前业界标准的密码哈希方案
- **产出文件**：`AuthController.java`, `UserService.java`, `UserServiceImpl.java`, `RegisterRequest.java`, `UserVO.java`
- **联调验证**：
  ```bash
  curl -X POST http://localhost:8081/api/v1/auth/register \
    -H "Content-Type: application/json" \
    -d '{"username":"testuser","password":"123456","email":"test@example.com"}'
  # 预期：返回 200 + 用户信息 JSON（不含 password_hash）
  # 验证：curl 相同请求第二次 → 返回 409 "用户名已存在"
  ```

#### PR-011：用户登录 API + JWT Token 签发

- **模块**：`[backend]`
- **需求来源**：F6.1（用户登录）
- **技术方案**：

- **关键决策**：JWT 无状态 vs Redis Session——选 JWT，因为移动端+桌面端多端登录，无状态 Token 更适合；Token 黑名单功能后续用 Redis 实现（PR-019）
- **产出文件**：`JwtUtil.java`, `LoginRequest.java`, `LoginResponse.java`
- **联调验证**：

  ```bash
    -H "Content-Type: application/json" \

  # 验证：curl 错误密码 → 返回 401 "用户名或密码错误"
  ```

- **技术方案**：
  - 定义 `asr.proto`：
    ```protobuf
    service AsrService {
      rpc StreamRecognize(stream AudioChunk) returns (stream AsrResult);
    }
    message AudioChunk { bytes data = 1; int32 seq = 2; }
    message AsrResult { string text = 1; bool is_final = 2; float confidence = 3; }
    ```

- **关键决策**：gRPC 而非 REST + SSE——gRPC 双向流天然适合「持续上传音频 + 持续接收文本」的场景，且 Protocol Buffer 比 JSON 更省带宽

#### PR-031：Go 网关环境噪声等级检测

- **模块**：`[gateway]`
- **需求来源**：F2.1（噪声检测）、痛点 P3（嘈杂环境）
- **技术方案**：
  - 计算音频帧的 **RMS（均方根能量）** 和 **SNR（信噪比估计）**
    ```
    RMS = sqrt(mean(samples²))
    噪声等级判定：
    - RMS < 500   → 静音
    - RMS 500~2000 → 安静
    - RMS 2000~8000 → 一般
    - RMS 8000~20000 → 嘈杂
    - RMS > 20000 → 极噪
    ```
  - 每 500ms 采样一次，取最近 3 次中位数作为当前等级
  - 将噪声等级附加到 AudioChunk metadata 中一并转发
- **关键决策**：RMS 简单阈值而非深度学习分类——轻量、延迟低，Go 中几行代码即可实现，无需引入 TensorFlow/PyTorch；后续可升级为 DNN 分类
- **产出文件**：`gateway-go/internal/audio/noise.go`
- **联调验证**：
  - 启动 Go 网关 → wscat 连接 → 分别发送安静/嘈杂测试音频
  - 日志观察：`noise level: quiet` / `noise level: noisy`

#### PR-032：Go 网关基础 Wiener 滤波降噪

- **模块**：`[gateway]`
- **需求来源**：F2.2（自适应降噪）、痛点 P3（嘈杂环境识别率）
- **技术方案**：
  - 实现频域 Wiener 滤波：
    1. 音频帧加窗（Hamming window，1024 samples）
    2. FFT → 频域
    3. 估计噪声功率谱（前 200ms 静音段平均）
    4. Wiener 增益：`G(f) = max(Ps(f) - Pn(f), 0) / Ps(f)`
    5. IFFT → 时域 → Overlap-add 重建
  - 仅当噪声等级 ≥ 「嘈杂」时触发降噪（节省 CPU）
- **关键决策**：Wiener 滤波在 Go 中纯自实现——Go 标准库 `math/cmplx` 支持复数运算，FFT 用 `github.com/mjibson/go-dsp/fft` 库（MIT 协议）。降噪放在网关层而非客户端——云端 ASR 路径必经网关，一处降噪全局受益
- **产出文件**：`gateway-go/internal/audio/denoiser.go`
- **联调验证**：
  - wscat 发送嘈杂测试音频 → Go 日志显示 `denoising applied, SNR improved from 5dB to 12dB`
  - Python ASR 返回的识别结果比不降噪时更准确

## 7. 风险管理

| 风险 | 概率 | 影响 | 单人开发特有缓解措施 |
|------|------|------|-------------------|
| Qwen3-ASR 模型下载慢/失败 | 中 | 中 | 提前下载模型到本地，Dockerfile 用本地路径；备选→先用 Whisper tiny 验证链路 |
| 无 GPU 导致云端推理太慢 | 高 | 中 | ONNX Runtime CPU + INT8 量化，1.7B CPU 推理约 3~5x 实时，功能验证够用，不追求实时延迟 |
| Android IME 生命周期 bug | 高 | 中 | 参考 [FUTO Keyboard](https://github.com/futo-org/android-keyboard) 开源 IME 实现；每个 IME 相关 PR 至少真机测试 |
| ONNX Runtime Android 集成报错 | 中 | 高 | 先用官方示例 App 跑通 ONNX Runtime → 逐步替换为自己的模型；备选：PyTorch Mobile |
| 单人精力/进度不够 | 中 | 高 | 严格按 PR 优先级：P0 必做 → P1 尽量 → P2 可放弃。最差情况：保证 Phase 0~3 完成（端云 ASR + 路由 = 核心价值），Phase 4~6 缩减 |
| 跨设备同步测试需要两台设备 | 低 | 低 | Android 模拟器 + 真机 = 「两台设备」；Desktop 同一台电脑另一个用户运行 |
